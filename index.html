⚙️ Backend senaryosu: Siparişlerim nasıl açılır?

Bir alışveriş sitesinde “Siparişlerim” düğmesine bastığında:

  1. Tarayıcı: Düğmeye tıklanınca sipariş listesini almak için istek hazırlar.
  2. HTTP isteği: GET /api/orders isteğini HTTPS üzerinden oturum çerezi veya erişim belirteciyle gönderir.
  3. API Endpoint: Backend routing, HTTP metodu ve yolu siparişleri listeleyen işlemle eşleştirir.
  4. Authentication Middleware: Oturum veya token doğrulanarak kullanıcının kimliği belirlenir; kimlik doğrulanamazsa 401 döner.
  5. Authorization: Kullanıcının bu listeye erişim yetkisi kontrol edilir ve sorgu yalnızca kendi siparişleriyle sınırlandırılır.
  6. Backend Controller / Service: İstek işlenir ve siparişleri getiren iş kuralları çalıştırılır.
  7. Database: Parametreli sorgu kullanıcı kimliğine ait siparişleri okur.
  8. JSON Response: Backend sipariş verisini uygun HTTP durum koduyla JSON yanıtı olarak gönderir.
  9. Tarayıcı: Gelen veriyi “Siparişlerim” ekranında gösterir.
🗄️ Database senaryosu: E-posta ile giriş nasıl çalışır?

Kullanıcı e-postasını ve parolasını giriş formuna yazdığında:

  1. Backend: HTTPS üzerinden gelen giriş isteğini alır ve girdileri doğrular.
  2. SQL Query: SELECT id, password_hash FROM users WHERE email = $1 sorgusunda e-postayı parametre olarak bağlar.
  3. Index: Sorgu planlayıcısı uygun bulursa email indeksini kullanarak bütün tabloyu taramadan ilgili kayda erişebilir.
  4. Users Table: Kullanıcıların kimlik, e-posta ve parola hash’i gibi alanları tabloda tutulur.
  5. Kullanıcı Kaydı: Eşleşen satırdan kullanıcı kimliği ve parola hash’i alınır.
  6. Şifre Hash Kontrolü: Backend, parola doğrulama kütüphanesiyle girilen parolayı tuzlanmış hash’e karşı doğrular; parolalar düz metin olarak saklanmaz.
  7. Session / Token: Doğrulama başarılıysa backend oturum oluşturur veya token verir; sonraki isteklerde kimlik ve erişim yetkisi yine denetlenir.

İndeks kaydı bulmayı hızlandırabilir; parolayı doğrulamaz. Parola saklamak için Argon2id gibi bu amaçla tasarlanmış bir hash yöntemi kullanılır.

🛡️ Web Güvenliği senaryosu: Güvenli oturum açma
  1. Tarayıcı: Kullanıcı giriş formuna e-posta ve parolasını yazar.
  2. HTTPS / TLS: Tarayıcı sunucu sertifikasını doğrular; form verisi aktarım sırasında şifreli ve bütünlüğü korunarak gönderilir.
  3. Backend: Girdileri doğrular, parametreli sorguyla kullanıcı kaydını arar ve aşırı denemeleri sınırlar.
  4. Authentication: Kullanıcının iddia ettiği kimliği doğrulama süreci yürütülür; bu süreçte parola kanıtı kontrol edilir.
  5. Password Hash Verification: Parola doğrulama kütüphanesi girilen parolayı kayıtlı tuzlanmış hash’e karşı denetler; düz metin parola saklanmaz.
  6. Session veya Token: Başarılı girişte uygun süre ve korumalarla oturum veya token oluşturulur; oturum çerezine uygun Secure, HttpOnly ve SameSite ayarları uygulanır.
  7. Yetkili API isteği: Backend her istekte kimliği ve kaynağa erişim yetkisini ayrı ayrı kontrol eder; giriş yapmak bütün siparişleri görme izni vermez.

HTTPS aktarımı korur; sitenin dürüstlüğünü veya uygulamanın hatasız olduğunu garanti etmez.

🚀 DevOps senaryosu: GitHub Pages’e kontrollü yayın

GitHub Pages kaynağı GitHub Actions olarak ayarlanmış ve uygun workflow tanımlanmış bir depo örneği:

  1. Kod değişikliği: Geliştirici index.html içindeki sözlük verisini günceller.
  2. Git Commit: Kontrol edilen değişikliği açıklayıcı bir mesajla yerel geçmişe kaydeder.
  3. Git Push: Commit’leri GitHub’daki dala gönderir; commit ve push ayrı işlemlerdir.
  4. GitHub Actions: Workflow’da tanımlı main push olayı yayın akışını tetikler; PR kontrolleri yayınlamadan ayrıca çalıştırılabilir.
  5. Build / Test: Statik dosyalar doğrulanır; bu tek dosyalı projede derleme zorunlu değildir, yayın dosyaları Pages artifact’i olarak hazırlanır.
  6. Deployment: Uygun izinlerle Pages dağıtım işi artifact’i yayınlar; hata varsa yayın durdurulur.
  7. Canlı web sitesi: Başarılı dağıtımdan sonra ziyaretçi yeni HTML/CSS/JS dosyalarını alır; etkileşimler tarayıcıda çalışır.

Pages dal/klasör kaynağından da yayınlanabilir; genel amaçlı backend çalıştırmaz.

☁️ Cloud senaryosu: Kampanya trafiğini karşılama
  1. Kullanıcılar: Kampanya başlayınca çok sayıda tarayıcı mağazaya bağlanmak ister.
  2. DNS: Alan adı CDN veya yük dengeleyicinin uygun adresine çözülür; DNS tüm paket rotasını belirlemez.
  3. CDN / Load Balancer: CDN önbellekteki görselleri yakın noktadan sunar, dinamik istekler sağlıklı backend örneklerine dağıtılır.
  4. Birden fazla Backend Instance: Yatay ölçekleme daha çok örnek ekler; auto scaling bunu kurallara göre yapabilir ve farklı zone’lar tek hata alanına bağımlılığı azaltır.
  5. Cache / Database: Önbellek tekrar eden okumaları azaltır; kalıcı veri veritabanında tutulur ve bu katmanın kapasitesi ile erişilebilirliği ayrıca planlanır.

Yük dengeleme tek başına yüksek erişilebilirlik sağlamaz: sağlık kontrolleri, oturum yönetimi, veri katmanı ve devralma tasarımı birlikte ele alınır.
